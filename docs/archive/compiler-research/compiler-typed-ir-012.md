# COMPILER-IR-012 — Resumable whole-function typed IR scheduling

**Status:** Implemented on the existing draft branch; **native semantic parity accepted** in bounded Minecraft 26.3 / Java 25 testing; **CPU benefit not established**, feature research-only and off by default (2026-11-19).

**Branch and PR:** `work/compiler-coverage` · [PR #10](https://github.com/qwasdf-1/mcfunction-compiler/pull/10), intentionally draft, open and unmerged. Builds on [IR-008](compiler-typed-ir-008.md) through [IR-011](compiler-typed-ir-011.md).

## Compiler problem and architecture

The IR-008/009 compiler emitted real Java/ASM scoreboard arithmetic but retained Minecraft's surrounding function call machinery. A regular `CallFunction` opens a child `Frame` and asks `ContinuationTask` to lazily materialize work. A compiled IR function already has large generated bytecode chunks, so the next opportunity is not a different `ScoreAccess` micro-operation but eliminating the *function's* redundant child-frame/continuation work where it is semantically safe.

The repository already includes the very narrow `DirectSchedulerPrototype` for repeated literal `scoreboard players add #x fc_sched 1` commands. **IR-012 generalizes the call-site experiment to complete, immutable typed-IR programs** instead of replicating that one command's implementation.

### New code: `TypedScoreIRDirectScheduler`

- On function construction, `TypedScoreIR.compile` continues the existing exact typed command lowering, compiling runs into **2–64-command generated JVM regions**. It records a direct-call candidate **only when all original function entries lower to typed IR and every region emits bytecode successfully**. Eligibility excludes every `PlainTextFunction` with an unsupported instruction, `function` or other command barrier, macro, selector/fork, compiler failure, or an uncompiled singleton tail. Minimum original length is 2, maximum is 4,096; e.g. 64, 128, 256, and 2,000 original commands are eligible, but 65 with a final isolated vanilla line is not.
- `CallFunctionMixin` adds a guarded interception at the **CallFunction execution stage** (not `/function` parsing). It requires an eligible compiled-function marker, `returnParentFrame == false`, an **empty function result callback**, an **empty source result callback**, no active tracer, a server `CommandSourceStack`, and a positive command quota. Ineligible calls **delegate to original Minecraft CallFunction** without changing any work.
- For an eligible call, the direct scheduler charges **the one vanilla function-call quota debit**, then stages a `CommandQueueEntry` for the first compiled chunk on the parent frame. No new child frame or vanilla continuation is created **only under this strict callback/return/tracing proof boundary**.
- A new immutable `Resume(source, chunks, pc)` implements `EntryAction`. One queued continuation runs exactly **one existing generated ASM region**, retaining all typed-IR per-command quota checks, scoreboard feedback, overflow, objective missing/read-only fallback and result semantics. If quota remains and a later chunk exists, it queues `Resume(..., pc+1)` through `ExecutionContext.queueNext`, permitting Minecraft's ordinary staging and sibling queue machinery to remain in control. It neither constructs all body queue entries up front nor nests Java function calls recursively.
- The already-existing typed IR `CompiledFunction` retains its original `PlainTextFunction` plus the normal compiled `entries()` as a **full vanilla-scheduling fallback**. `CallFunctionMixin` also restores original logical function line counts in `TraceCallbacks.onCall` for typed-IR fallback/traced functions. The pre-existing direct scheduler and other mixins remain intact.

This is genuinely resumable across chunk boundaries, but **does not suspend across server ticks**. Minecraft functions still execute within the outer command's queue and quota; the continuation is a heap queue cursor, not asynchronous work.

### Opt-ins and controls

The new feature is entirely disabled absent `FC_TYPED_IR_DIRECT_FUNCTION=true` in addition to `FC_WRAPPER_PROBE=true`, `FC_TYPED_IR_MODE=bytecode` and `FC_TYPED_IR_NAMESPACE=<explicit namespace>`. When the separate `FC_TYPED_IR_DIRECT_FUNCTION_TOGGLE=true` is set, `fc_ir012_direct on|off` flips only the call-site path during a single JVM session. Normal typed ASM bytecode and original command sources are identical across both benchmark arms.

A separate **test-only** `FC_TYPED_IR_DIRECT_FUNCTION_HARNESS=true` permits `fc_ir012_call fc_ir:ir012_*`, an empty-result-callback call site matching the existing `fc_arch_call` harness. Ordinary public `/function`, `/debug function`, stored-result calls and other nonempty callback contexts retain Minecraft's normal call behavior. The harness has a hard namespace/path gate and is not registered by default.

`FC_TYPED_IR_DIAGNOSTICS=true` reports function eligibility, executed direct calls, callback/tracer fallbacks, generated chunk executions, and resumed chunks through the existing `functioncompiler ir008` diagnostic command; these counters are **off during CPU timing**. The IR-010 source-score cache and IR-011 singleton feedback optimization were explicitly **disabled in all IR-012 arms**, avoiding confounded optimization stacks.

## Native semantic acceptance — passed

[Actual four-arm Minecraft 26.3 / Java 25 CI run #44677624470](https://github.com/qwasdf-1/mcfunction-compiler/actions/runs/44677624470) · [Raw per-arm scoreboard observations, server logs, and CPU block data (artifact #14602389948)](https://github.com/qwasdf-1/mcfunction-compiler/actions/runs/44677624470/artifacts/14602389948)

**Four fresh Minecraft JVMs** ran an identical disposable original-source datapack: (1) unwrapped vanilla, (2) typed interpreted IR, (3) generated bytecode with direct scheduling disabled, and (4) generated bytecode with direct resumable function scheduling enabled. Every mode passed and produced identical **63 observed scoreboard-state cases**. The cases included:

- Complete typed-IR mixed set/add/remove, binary `+=` / `*=` / `=` and single-stage `if` / `unless` source;
- Whole-function bodies of 64, 128, 256, and **2,000 original commands**, proving one or multiple ASM continuations; exact command order and total scores;
- A deliberate unsupported nested function barrier and an **uncompiled last command after the first 64**, both rejected for whole-function direct scheduling;
- Missing objective fallback inside typed regions, public `/function` callback fallback, stored function result, debugger trace fallback and restoration of the original line count;
- Verified `minecraft:max_command_sequence_length` quotas **1, 2, 3, 4, 5, 6, 8, 10, 16, 32, 65, 130, 300**, with partial-score states compared to vanilla after every test.

**Activation evidence in the direct ASM native arm** (with diagnostics on):

| Counter | ASM direct | ASM with direct off |
| --- | ---: | ---: |
| Typed IR regions compiled | 44 | 44 |
| Generated ASM regions | 44 | 44 |
| Whole-function direct candidates at compilation | 6 | 6 |
| Direct function calls admitted | **43** | **0** |
| Compiled chunks executed by direct scheduler | **81** | 0 |
| Non-initial queued chunk resumptions | **41** | 0 |
| Attempts deferred to vanilla due to callback/tracer/return guard | **3** | 0 |

**Why the counters differ:** A direct call may consume its final quota debit before its first body chunk is dequeued, and therefore a call admission does not necessarily produce a first-chunk execution. Likewise a call may stop partway through a chunk. The runtime never treats total direct calls as equivalent to body completions; every observed score is compared with vanilla.

Development-only failures excluded from this accepted run: a static test initially expected the Java variable `context.incrementCost()` instead of its typed alias `engine.incrementCost()`; the trace helper needed to be public for its subpackage Mixin; and the test-only bytecode-off arm initially lacked permission to toggle its own research control. All were corrected and the final native gate completed successfully.

## Same-generated-ASM CPU crossover — no causal speedup established

The exact *same* compiled 256-line `scoreboard players add #x fc_ir 1` function was invoked through the same empty-callback harness for both modes. The A/B toggle changed only whether `CallFunction` used vanilla child-frame/continuation scheduling or the IR-012 generated-chunk program counter. The 256-line function comprises **four generated 64-command regions**. Every timed window executed **120 invocations × 256 original score writes = 30,720 writes** and checked the resulting scoreboard state.

- **Two fresh Minecraft server JVM boots.** Each boot ran four counterbalanced ABBA/BAAB on-versus-off four-window blocks and two same-path off/off A/A control blocks.
- **Eight** primary comparison blocks and **four** A/A controls, with every observed final score and work count valid.
- Median direct-scheduler Server-thread running CPU difference **−4.085%** (negative means faster).
- Per-JVM medians were **−10.597%** and **+7.731%** — the two boots disagree in direction.
- Individual direct-vs-vanilla blocks spanned **−21.963% to +18.757%**.
- Same-path A/A median was **+18.548%**, with a range **+0.173% to +47.109%**. The controls are noisy enough to materially weaken the apparent improvement.

**Interpretation:** The bounded native semantics are supported and the new scheduler does remove function-level scheduling machinery on the accepted path. But the measured speed difference is within large same-path variation and not robust across boots. This is **directional, inconclusive evidence**, not a statistical or practical speedup on real datapacks. Two JVM boots do not establish independent-server 95% confidence or the project's 15% promotion target. No production default change is warranted.

## Safety boundary and follow-up

IR-012 intentionally does **not** attempt to inline unsupported commands, arbitrary nested calls, `/return`, forks, macros, or function/result callback paths. These keep ordinary `CallFunction` and its child frame.

**Important limitation:** The existing IR-008/009 compiled region batches 2–64 original commands within one queue action. A mod that synchronously queues new work from a scoreboard mutation or feedback callback *inside that region* may observe a different queue interleaving than vanilla's single-command scheduling. IR-012 does not solve or prove away this prior cross-mod observability issue. The new direct path also removes the child frame only when no callbacks/tracer/return mode are present, not for all Minecraft function consumers. No exhaustive external mod, debug trace-file, reload, or re-entrant callback compatibility proof was performed. It must stay research-only.

**Disposition:** Keep the architecture on the draft branch as a verified program-counter experiment, but **do not enable by default or merge as a general scheduler replacement**. The most valuable next task is to model and test re-entrant queue effects at chunk boundaries and expand function-level IR/control-flow acceptance only after proving the resulting trace, return and callback semantics. Prefer representative real datapacks and controlled independent server comparisons before considering promotion.
