# SCHED-ATTR-028 — concrete result-consumer routing and callback effects

**Status:** Phase A exact Minecraft 26.3 callback-routing inspection completed. Phase B native sampled delegate-class attribution **preregistered below, no native measurements accepted yet**. Research-only branch stacked on accepted [SCHED-ATTR-027](brigadier-plumbing-SCHED-ATTR-027.md).

## Hypothesis and important limits

In the previous three-arm native screen, `ResultConsumer.onCommandComplete` had a control-subtracted descriptive mean ~102.61 µs in a 1-in-32 sampled `ExecuteCommand` subset, extrapolated to ~21.43% of the event Server-thread CPU. There were 857 successful callbacks and 15 failure callbacks in 872 matched TIMED samples. `CommandContext.copyFor` was near the timer-control floor. This is **inclusive callback CPU**, not scheduler waste, recoverable CPU, or evidence that result handling can be skipped.

The next question is *which runtime result-consumer implementations and delegate callbacks actually run in this same Vein Miner fixture,* and whether their CPU is necessary state-changing work (scoreboard writes, return values, command success-count handling, nested function continuations) rather than repeated routing/dispatch bookkeeping.

## Phase A — pinned bytecode inspection

Before selecting any Mixin/classification targets, inspect the exact Java 25 / Minecraft 26.3 runtime classes `ExecutionCommandSource`, `CommandSourceStack`, `CommandResultCallback`, `Frame`, `ExecutionContext`, `ExecuteCommand`, `CallFunction`, `BuildContexts`, and Brigadier `ResultConsumer`/`ContextChain`, with `javap -p -s -c`. Verify the official Mojang 26.3 server SHA from `source-versions.lock`, separately record the nondeterministic Loom-generated development jar and resolved Brigadier jar fingerprints, and archive every disassembly as-is. Explicitly identify where the `ResultConsumer` for `ExecuteCommand` is obtained, its concrete receiver, how it delegates to underlying `CommandResultCallback` and any function-frame callbacks, and what exact methods mutate scoreboard/return state.

A static class name or JVM lambda identifier alone does not prove callback side effects or CPU. If the callback receiver is an adapter capturing a source or frame, the correct next hook must classify **its delegate and effects**, not just the common adapter's class name.

## Phase A: accepted official-source bytecode mapping (November 18, 2026 UTC)

[Public GitHub Actions #44241010647](https://github.com/qwasdf-1/mcfunction-compiler/actions/runs/44241010647) completed the pinned Java 25/Fabric build and exact routing inspection, archived as [raw artifact #14399925998](https://github.com/qwasdf-1/mcfunction-compiler/actions/runs/44241010647/artifacts/14399925998). The immutable official Mojang 26.3 server SHA-256 verified; the nondeterministic Loom development jar and resolved Brigadier jar SHA values are recorded separately.

**Key evidence, not an inferred callback hierarchy:**

1. `ExecuteCommand.execute` passes `ExecutionCommandSource.resultConsumer()` to `ContextChain.runExecutable`. In Minecraft 26.3 bytecode, `resultConsumer()` simply returns an `invokedynamic` **stateless adapter**. Its `lambda$resultConsumer$0` loads `CommandContext.getSource()`, casts to `ExecutionCommandSource`, calls `callback()`, and invokes that **underlying `CommandResultCallback.onResult(success,result)`**. Profiling the adapter class alone would never identify the downstream state-changing implementation.
2. `CommandSourceStack.callback()` returns its immutable `resultCallback` field. `withCallback` creates/returns a source with a callback. A non-empty `CommandResultCallback.chain(first,second)` creates a lambda which sequentially calls `first.onResult` then `second.onResult`. If either argument is the singleton `EMPTY`, the chain method immediately reuses the other delegate rather than wrapping it.
3. `Frame` independently owns a `returnValueConsumer` used by `returnSuccess` / `returnFailure`. Do not assume each leaf's source callback is identical to the surrounding function frame's return callback.
4. Class names of Java hidden lambdas are not stable across JVMs (e.g. suffixes `/0x...`) and may represent multiple callsites under the same owner. Normalizing a class name to a declaring owner is a **coarse implementation family**, not proof of the leaf delegate or underlying game mutation.

### Phase B: locked before native measurement — bounded callback delegate-class census

Run exactly **three independent Minecraft 26.3 / Java 25 native Vein Miner boots** in the frozen PLAIN, EMPTY and TIMED order, all normal cached ScoreAdd. Reuse the unchanged SCHED-ATTR-027 event, pinned publisher ZIP SHA-256 `fa5fbfc08b54a881ec1cf255fdc2e7714c258e451d17c626309cbf5988df6e4e`, **215 ore operations / 1,952 queue-head advances**, identical final source/block/scoreboard/markers, 9-second pre-event stable tick baseline, zero cgroup throttling, ≤25% server runqueue delay, and `/proc` Server-thread CPU. No Spark/JFR/other command counters.

Activate `FC_SCHED_RESULT_DELEGATE_TRACE` only for this study. **Do not add another CPU clock**: on each original 1/32 selected ExecuteCommand result-consumer call, close the existing `SchedulerPhaseCpuProbe.RESULT` interval, then read the command context's source callback and record its *actual Java delegate class owner*, outcome (success/failure) and **the raw inclusive nanos already measured by the parent**. Class-lookup/hash-map maintenance is entirely **outside** that interval. PLAIN performs no selected timings and accumulates no delegate records; EMPTY accumulates class/outcome counts but not real-duration CPU; TIMED associates the existing raw callback durations with the observed implementation families. No callback is suppressed, replaced, reordered, cached or executed twice. Classify the source callback, not the universal stateless Brigadier ResultConsumer.

**Critical transport constraint:** The pre-existing all-purpose `function_compiler_probe status` response reaches the **4,096-byte RCON boundary**. Do not append another histogram there. Query a separate research-only `fc_sched_delegate_summary` command **after** the event CPU window closes. Limit to 14 distinct class labels plus overflow; cap reply at 3,300 characters and reject malformed/truncated summaries. Retain the full resulting JSON and exact histogram conservation against SCHED-ATTR-027's callback timing stream and 857/15 success/failure categories as observed in the earlier *different* run (new-run counts may differ).

**Predeclared gates:** Preserve every original SCHED-ATTR-027 workload/host/clock and 3-arm parity gate. Native class counts sum exactly to the selected `ResultConsumer` samples; the class-level raw CPU sums exactly to the original TIMED `RESULT` CPU-sample sum, and outcome counts sum to the original same-arm success/failure count; all records come from the Minecraft Server thread. In the PLAIN/OFF arm all new counters remain zero. Require at least **200 selected callbacks** in each enabled arm, and match EMPTY/TIMED total selected calls within **15%**. A label with at least **30 samples** in TIMED and ≤**15%** count difference relative to EMPTY is suitable for a descriptive per-group screen; smaller or unmatched classes are preserved as **insufficiently exposed**, not dropped. Reject if more than **5%** of TIMED selected calls fall into the `OTHER` overflow bucket (coarse class cardinality too high for a useful ranking). Do not relax thresholds after observing a result.

**Analysis and limitations:** Sort the TIMED class labels by **raw inclusive sampled callback CPU** and report within-sample fractions, counts and callback outcomes. This identifies the groups **dominating the observed sample**, not necessarily the population of all command callbacks. For context only, use SCHED-ATTR-027's global mean EMPTY result-clock pair as a *uniform* clock-cost sensitivity subtraction per class; this is **not a separately measured per-class calibration** or an exclusive CPU statistic. Preserve negative differences. One independent JVM per arm; no causal speedup, confidence interval or proof of 1/32 representativeness. Java lambda owner normalization may merge different concrete capture sites; `CommandResultCallback.chain` represents a wrapper and can conceal the underlying leaf callbacks. If **CHAIN dominates**, the next independent experiment must instrument its child delegations or trace exact callback construction before claiming that any specific command-effect implementation dominates.

This is research-only, the new tracing class and query command must be **disabled by default**, the specific research workflow must return to `workflow_dispatch`-only after evaluation, and the PR must remain **draft**. Installed-but-disabled Mixin overhead has not yet been independently measured.
