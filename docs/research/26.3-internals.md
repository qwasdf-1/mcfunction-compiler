## Execution cost and queue boundary

- `ExecutionContext.incrementCost()` subtracts one from `commandQuota`; it does
  not itself check whether the quota is exhausted.
- `ExecutionContext` construction copies the supplied command limit into both
  `commandLimit` and the initial `commandQuota`. The active context therefore
  keeps its captured quota when a command changes the gamerule; later contexts
  receive the updated gamerule value.
- `runCommandQueue()` checks `commandQuota <= 0` before polling the next queue
  entry. It executes that entry, handles queue overflow, moves newly queued
  entries onto the front of the main deque, then loops back to the quota check.
- Therefore, a debit that takes the quota to zero during an entry does not
  interrupt that already-running entry. The next queued entry is stopped at the
  next loop check. This is a source-level fact; low-quota direct-function
  scoreboard outcomes now match across vanilla and both Fabric wrapper modes,
  though the pure vanilla process is not instrumented for individual debits.
- A bytecode reference scan across all 7,744 `net/minecraft` classes in the
  inspected merged-deobf artifact found only the `incrementCost` definition
  plus three direct caller classes:
  `CallFunction`, `BuildContexts`, and `ExecuteCommand`. `javap -c` confirmed the
  call instructions in those three classes. This inventory covers vanilla
  Minecraft classes, not mod code.
- `CallFunction.execute` charges once per function call, invokes `onCall` when a
  tracer is installed, makes a child frame, and schedules the function entries
  through `ContinuationTask`.
- The built-in `BuildContexts` path charges once for each non-null redirect
  modifier stage before expanding its sources. `CustomModifierExecutor` returns
  through its own path before that built-in debit. A normal built-in leaf is
  scheduled as an `ExecuteCommand`; that entry charges once per expanded source,
  runs the executable, sends result callbacks, and reports the return value to
  the tracer.
- `CustomCommandExecutor` branches bypass the built-in `ExecuteCommand` leaf.
  Vanilla function commands schedule `CallFunction` entries, so their function
  calls still debit there. `execute if function` uses isolated frames and
  schedules `CallFunction` entries before continuing the modifier chain.
  `return value` and `return fail` use custom leaf executors with no direct
  debit; `return run` uses a custom modifier path, then runs its following
  command through normal context construction. These paths confirm that source
  lines are not a reliable unit of quota cost.

## Function construction and reload

- `ServerFunctionLibrary.reload` resolves function resources and starts
  `CommandFunction.fromLines` work asynchronously. `fromLines` handles
  continuation lines and comments, validates lines, and parses ordinary
  commands through Brigadier. It flattens each parsed context and stores a
  `BuildContexts.Unbound` action.
- `FunctionBuilder.build` returns a `PlainTextFunction` for a non-macro function
  and a `MacroFunction` when macro entries exist. In the exact 26.3 classfile,
  `PlainTextFunction.instantiate` consists of `aload_0; areturn`; it returns
  the existing object without parsing or rebuilding entries. Macro templates
  are substituted and parsed on instantiation cache misses; the current macro
  cache is an equality-keyed LRU of eight parameter tuples.
- After parsed function futures complete, reload assigns its function map and
  then resolves tags through `TagLoader`, whose lookup uses the library's
  function map. These maps belong to the newly built `ServerFunctionLibrary`;
  `MinecraftServer` supplies it to `ServerFunctionManager.replaceLibrary` only
  after the complete server resource reload succeeds. The manager then replaces
  its library reference, snapshots the tick tag, and schedules the load tag for
  the next normal tick. A wrapper returned at the builder boundary is therefore
  visible to tag resolution before publication.
- `MinecraftServer.reloadResources` schedules resource loading and applies the
  completed resources on the server executor. When called on that same server
  thread, it uses `managedBlock` until the reload future completes. The vanilla
  `/reload` command calls it from the server thread. The concurrency probe calls
  the same reload method from a test-only background thread so the server can
  continue servicing function lookups while preparation is held.
- `ServerFunctionManager.execute` and function-tag execution instantiate a
  function and queue it through vanilla's `ExecutionContext` and
  `CallFunction`. `FunctionCommand` also uses `CallFunction`. `/debug function`
  traces through `CallFunction` and records the instantiated entry count.

These facts make a construction-time wrapper a plausible integration candidate.
`FunctionBuilder` is package-private. Runtime probes now verify Mixin
application, custom-tag identity, delegation, debug parity, and identity across
sequential and one held background reload. They do not establish broad mod
compatibility or a performance gain.

### Entity NBT used to build function macro arguments

The exact 26.3 call path for `function <macro> with entity <selector> <path>`
is relevant to the PERF-011 Vein Miner profiles. The entity `ArgProvider`
returns an `EntityDataAccessor`; `FunctionCommand$2.arguments` obtains the
parsed NBT path and calls `FunctionCommand.getArgumentTag`. That calls
`DataCommands.getSingleTag`, which calls `DataAccessor.getData()` **before**
applying the NBT path. For entity access, `EntityDataAccessor.getData()` calls
`NbtPredicate.getEntityTagToCompare`, which creates a `TagValueOutput` and
calls `Entity.saveWithoutId`. Thus a narrow path such as `data` still builds
the serialized entity compound before selecting the one requested value.

The same pinned `Entity.saveWithoutId` bytecode writes the entity's `CustomData`
component under the top-level `data` key when it is nonempty. The public
`Entity.get(DataComponents.CUSTOM_DATA)` method returns that component, and
`CustomData.copyTag()` returns a deep copy. These provide a possible vanilla
fast path for a literal top-level `data` lookup, subject to exact empty-tag,
error, mutation, mixin, and mod-compatibility checks. They do not establish that
the shortcut is safe for arbitrary entity NBT paths or modded serialization.

Macro functions also retain only the names they reference in their private
parameter list. A more aggressive projection could pass only those parameter
values when the target is a known macro function. That requires proving the
target function set, missing-key errors, compound-valued parameters, and
fallback behavior; it remains a separate experimental design decision.

## Cross-version comparison

The same `javap -p -s -c` inspection was run on Loom-produced
`minecraft-merged-deobf` classfile artifacts derived from the official server
bundles for Minecraft 26.1.2, 26.2, and 26.3. Both the official bundle and
inspected classfile artifact fingerprints are in
[`source-versions.lock`](source-versions.lock). For the inspected function and
execution surface, normalized disassembly showed:

- `ExecutionContext`, `CallFunction`, `BuildContexts`, the execution-task
  `ExecuteCommand`, `ContinuationTask`, `CommandFunction`, `FunctionBuilder`,
  `PlainTextFunction`, `MacroFunction`, `ServerFunctionLibrary`,
  `ServerFunctionManager`, `DebugCommand`, and `ReturnCommand` are unchanged
  across all three versions.
- The server command class `ExecuteCommand` has broader version changes, but
  `scheduleFunctionConditionsAndTest` has the same instruction sequence in all
  three after normalizing constant-pool indices and formatting. The method still
  instantiates the functions and schedules isolated `CallFunction` entries.
- `FunctionCommand`'s queueing and `CallFunction` construction are unchanged.
  The 26.3 class only changes an NBT argument provider's owner from
  `DataCommands.DataProvider` to `ArgProvider` in its command registration path.

This is a static comparison, not a runtime compatibility test. It reduces the
specific risk that the 26.3 scheduler or function-builder descriptors diverged
from 26.2; it does not establish Fabric Mixin application or API compatibility.

## Version adapter map

`javap -p -s` was run against the fingerprinted Loom classfile artifacts for
26.1.2, 26.2, and 26.3. The following hook and scheduler descriptors are
identical in all three artifacts:

| Surface | Named method and erased signature | Porting note |
|---|---|---|
| Queue and cost boundary | `ExecutionContext.runCommandQueue()V`; `incrementCost()V` | Same quota owner and queue entry point. Preserve both methods' behavior when adapting. |
| Function call entry | `CallFunction.execute(ExecutionCommandSource, ExecutionContext, Frame)V` | Same erased descriptor. A synthetic bridge taking `Object` is also present; target the typed descriptor. |
| Modifier expansion | `BuildContexts.execute(ExecutionCommandSource, List, ExecutionContext, Frame, ChainModifiers)V` | Same descriptor and method boundary. |
| Built-in command leaf | `execution.tasks.ExecuteCommand.execute(ExecutionCommandSource, ExecutionContext, Frame)V` | Same typed descriptor; a synthetic `Object` bridge is also present. |
| Function parsing | `CommandFunction.fromLines(Identifier, CommandDispatcher, ExecutionCommandSource, List)CommandFunction`; `parseCommand(CommandDispatcher, ExecutionCommandSource, StringReader)UnboundEntryAction` | Same parse entry and parsed action type. |
| Wrapper construction | `FunctionBuilder.build(Identifier)CommandFunction` | Same return type and builder hook. |
| Reload publication | `ServerFunctionLibrary.reload(SharedState, Executor, PreparationBarrier, Executor)CompletableFuture` | Same reload method descriptor; runtime reload parity still requires its own tests. |
| Function conditions | `server.commands.ExecuteCommand.scheduleFunctionConditionsAndTest(ExecutionCommandSource, List, Function, IntPredicate, ContextChain, CompoundTag, ExecutionControl, InCommandFunction, ChainModifiers)V` | Same method descriptor and instruction sequence. |

The server command class `net.minecraft.server.commands.ExecuteCommand` has
other version changes: its command-registration path changes the NBT argument
provider owner from `DataCommands.DataProvider` to `ArgProvider` in 26.3. The
function-condition scheduling method above is unchanged. The current project
build and Mixin configuration target 26.3 only; this descriptor map identifies
porting checks but does not claim that a 26.1.2 or 26.2 build, Fabric API, or
Mixin configuration works without a separate target-specific build and runtime
gate.

The original inspection artifact hash for 26.3 remains recorded above. The
current project cache contains a regenerated Loom classfile artifact with a
different whole-JAR hash; its official server input still matches the pinned
26.3 server SHA-256, and the method map was rechecked against this current
artifact. Both the original inspection hash and the current build artifact hash
are retained in `source-versions.lock` so the two inspection contexts are
distinguishable.
